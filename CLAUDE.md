## Status at a glance

- **Framework:** PySide6 (Qt 6 + Python + QML) — **staying native Qt/QML** (the 2026-06-05 Tauri pivot was reversed 2026-06-07; see the banner above). File-tree + git-status are reused from the FM's `Symmetria.FileManager.UI` QML module rather than reimplemented.
- **Core:** NeoVim runs as a TUI inside a `QMLTermWidget` (forked qmltermwidget — Konsole's VT engine) and draws its own grid; a `pynvim` RPC-only client attaches to its `--listen` socket for control + the chrome relays. User's real `~/.config/nvim` loads by default (plugins, colorscheme, keymaps all work).
- **Status bar:** native QML with mode badge, project, branch, file path, cursor position. Lualine is hidden from the viewport (laststatus=0 re-asserted on VimEnter).
- **Which-key overlay:** native QML panel driven by our own state machine + trie built from `nvim_get_keymap()` (plus which-key.nvim's preset catalog for built-in motion descriptions). Which-key.nvim itself is neutralized on VimEnter.
- **Constraints:** keyboard-first, Symmetria aesthetic, Vim-style navigation preserved.
- **Runtime deps on Arch:** `sudo pacman -S --needed pyside6 qt6-webengine python-pynvim python-watchdog` (`qt6-webengine` is NOT a hard dep of `pyside6` but IS required — `PySide6.QtWebEngineQuick` links `libQt6WebEngineCore.so`, and `app.py` imports it at module top for the browser surface, so the IDE won't start without it). **Agent browser-control AND agent coordination** additionally need `paru -S python-mcp` (AUR; pulls uvicorn/starlette) for the IDE-side MCP server — it hosts the three browser tools (`browser_open`/`browser_list_windows`/`browser_request_attention`) plus the ungated `wait_for_agent` coordination tool, so python-mcp matters in EVERY project, not just browser-opted ones — AND `node`/`npx` on PATH (Stage 4 drives the view via off-the-shelf `chrome-devtools-mcp`, fetched by `npx`). Both degrade gracefully: the MCP server start is non-fatal and backgrounded (a daemon starter thread — since 2026-07-03 it starts UNCONDITIONALLY, reversing the 2026-06-24 lazy per-project gating, because the `wait_for_agent` coordination tool rides it; never on the GUI thread; `SYMMETRIA_IDE_BROWSER_MCP=0` disables it). A missing `npx` just omits the chrome-devtools tools. Per-project gating (see 'The browser panes' Stage 5) now bites in two places, not at server injection: the chrome-devtools CONFIG entry (the per-agent Node process) and a CALL-time gate on the three browser tools; every agent always gets the `symmetria-browser` server entry itself (coordination must work everywhere) — so without npx/python-mcp, the IDE runs manual browsing only. - **Run:** `PYTHONPATH=src python -m symmetria_ide`.
- **Dev workflow doc:** `docs/dev-workflow.md` — env vars for headless smoke testing, Hyprland workspace-6 rule, notification-system quirks.
- **Branching:** this directory is the `dev` worktree — ALL development happens here. `~/projects/symmetria-ide-stable` holds `main` (the daily-driven build); never edit it, it only moves via user-initiated promotion. Full rules + promotion procedure: `docs/branch-workflow.md`.
- **⚠ NEVER pattern-kill the IDE process (`pkill`/`pgrep -f`) — it kills the user's daily-driver AND this session's own host.** Dev and stable *always* launch with a **byte-identical command line** (`python -m symmetria_ide`), and this session may itself live in a terminal pane inside the stable IDE — so `pkill -f symmetria_ide` / `kill $(pgrep -f …)` matches the stable instance and every dev instance across workspaces; no command-line pattern can target one safely. ## The capsule protocol

Lua emits `vim.rpcnotify(0, "capsule", { id = "...", label = "...", value = "..." })`. Python routes by id:

| id        | surfaced in                   | emitted on                                |
|-----------|-------------------------------|-------------------------------------------|
| `mode`    | `StatusBarState.mode`         | ModeChanged, VimEnter                     |
| `file`    | `StatusBarState.file`         | BufEnter, BufWritePost                    |
| `branch`  | `StatusBarState.branch`       | BufEnter, DirChanged                      |
| `project` | `StatusBarState.project`      | BufEnter, DirChanged                      |
| `pos`     | `StatusBarState.position`     | CursorMoved, CursorMovedI                 |
| `gitpoke` | nothing — intercepted, routed to `GitController.poke()` (debounced re-scan) | BufWritePost |
| anything else | `CapsuleModel` (generic)  | plugin-defined                            |

## The completion pipeline (separate from capsules)

For cmdline autocomplete, we run our own `getcompletion()`-based pipeline instead of relying on `ext_popupmenu` — plugin ecosystems (`nvim-cmp` with `cmp-cmdline`, `wilder.nvim`) draw their own floating windows anchored to the *default* bottom-row cmdline position, which looks broken once we've extracted the cmdline into a floating overlay.

Pipeline shape: `CmdlineEnter`/`CmdlineChanged`/`CmdlineLeave` autocmds in `runtime/init.lua` call `vim.fn.getcompletion(line, "cmdline")` and emit `vim.rpcnotify(0, "completions", { items, line, selected })`. Python subscribes to `"completions"` alongside `"capsule"` and routes payloads to `CompletionModel` (a `QAbstractListModel` with a single `word` role and a `selected` property). `CommandLine.qml` binds its popup exclusively to `completionModel`, so the popup is independent of whatever the user has installed.

Tab navigation works via a `c`-mode keymap installed at each `CmdlineEnter` (scheduled via `vim.schedule` so it wins over plugin keymaps that might also install during `CmdlineEnter`). The keymap calls a Lua `cycle_completion(direction)` that advances through the cached list and calls `setcmdline()` on the chosen item. `emit_completions` then fires from the resulting `CmdlineChanged`, but uses **equality-based cycle detection** (does the live cmdline text match any cached item?) to keep the list stable and emit the matching row as `selected` — this is robust regardless of whether `CmdlineChanged` fires synchronously or deferred.

We also force-disable `nvim-cmp`'s cmdline source from our `VimEnter` handler (`cmp.setup.cmdline(":", { enabled = false })`, plus `/` and `?`) so its floating popup doesn't render at the default bottom-row cmdline position. `noice.nvim` users still need to add their own `vim.g.symmetria_ide` guard since we don't override noice post-setup.

To add a new well-known capsule, add the field + notify signal to `StatusBarState` and bind it in `StatusBar.qml`. To add a plugin-defined one, just emit it from Lua — it falls through to `CapsuleModel` and a future delegate can render it.

## The terminal-agent runtime (IDE-native orchestrator)

Shipped 2026-06-10 — THE agent workflow inside the IDE. Agent CLI instances (Claude or OpenCode — see "Harnesses" below) run in IDE-owned `QMLTermWidget` panes on the `"agent"` central surface (one visible at a time, pool of 5), with an always-visible top bar carrying the sparkle bubbles plus the terminal/editor/agents surface switcher, and Symmetria Shell's `agent-bridge.py` as the single state hub. Replaces running orchestrator.nvim inside the embedded nvim (hard cutover — see "Chords").

**Harnesses.** A slot's agent CLI is its *harness* — `claude` or `opencode`, registered in `src/symmetria_ide/agent_harness.py` (pure module mirroring orchestrator.nvim `terminal.lua::M.backends` semantics: claude's dangerous mode is a flag, opencode's is the `OPENCODE_PERMISSION` nested allow-all env var — the nested form is load-bearing because OpenCode resolves permissions last-match-wins, so a flatter form loses to the user's own `ask` rules; see the module comment). Claude additionally carries `base_flags=("--no-chrome",)` on EVERY spawn (2026-07-13): the user's global `claudeInChromeDefaultEnabled` would otherwise auto-connect each agent to the Claude-in-Chrome extension MCP — the user's REAL Chrome — and agents picking it over the injected symmetria-browser tools breaks the browser containment principle (escaped Hyprland windows, no chip globe/attribution, flaky shared extension). The CLI flag beats the global default; there is no settings.json/env-var form. Do not remove it. In the spawn menu, `o` toggles between Claude and OpenCode, and every menu open resets the selection to Claude; n/c/r spawn in the selected harness. OpenCode resume requires a session id (`--session` has no picker form), so `r` on the OpenCode harness opens `qml/AgentSessionPicker.qml` instead of spawning directly. The picker lists `opencode session list --format json` (fetched on a one-shot daemon thread via `request_opencode_sessions`) and spawns `--session <id>` on accept. Tracking is harness-agnostic: both reporters (claude's hooks, `~/.config/opencode/plugin/symmetria-agent.js`) key on the same `SYMMETRIA_AGENT_ID`, and the instance payload's `agent_type` carries the harness to the bridge/dashboard.

**Per-project model/effort defaults.** A NEW agent's model + reasoning-effort are pinned per project via the committed `.symmetria/ide.json` marker's `harness_defaults` block (schema + example in `project_browser_marker.py`'s docstring), read by `harness_model_effort` and threaded through `agent_harness.spawn_argv` as per-harness launch flags — the flag names differ per harness (claude vs opencode) and the claude effort-validation set both live on `AgentHarness`; opencode's effort is an open-ended provider `--variant`, so it isn't validated. An absent value, or an out-of-set **effort**, appends no flag (harness default); a **model** is passed through unvalidated, so a bad model id fails the spawn rather than degrading (the valid-id set drifts per release — validating it would rot). This is the one-shot answer to the two-command `/model` + `/effort` friction: commit once, every agent in the project launches correct. **Note:** the marker is now MULTI-field (`browser_agents` + `harness_defaults`), so `set_browser_agents` is read-merge-write — a bare overwrite would wipe `harness_defaults` on a `Ctrl+Shift+M` browser toggle. Mid-session switching of a RUNNING agent now ships for the MODEL axis via `Alt+M`, which injects `/model` to open claude's OWN native picker (see 'Chords'); `/effort` extends the same way but isn't wired yet. An IDE-built combined model+effort picker is NOT planned — composing the CLI's own picker supersedes it.

**Topology.** Three cooperating pieces:

1. **`src/symmetria_ide/agent_bridge.py` — `AgentBridgeClient`.** One Unix-socket connection to `/run/user/$UID/symmetria-agents.sock` playing both protocol roles: *publishes* this IDE's agents with the same verbs orchestrator.nvim's `bridge.lua` speaks (`hello`/`sync`/`added`/`removed`/`focus`/`updated`/`goodbye`; `nvim_pid` = IDE pid, `buf` = slot; `hello` also declares `host_window_pid` so the bridge maps agents to the IDE's Hyprland window without the /proc walk), and *subscribes* (`{"type":"subscribe"}`) to consolidated snapshots. Reader thread owns connect/retry with capped backoff and replays hello→sync→subscribe on every (re)connect; GC suspended around cross-thread emits (gotcha #10); title updates debounced 200ms.
2. **AppController pool** (`app.py`): `_term_agents` slot records + QML props (`agentOrder`, `agentSlotActive`, `agentTitles`, `focusedAgent`, `agentActivity`, `maxAgentSlots`) and the slot API (`spawn_agent` — **dangerous=True is the default polarity**; `agent_spawn_argv` builds `["env", "SYMMETRIA_AGENT_ID=<pid>_<slot>", <harness executable>, ...]` (per-harness flags/env from `agent_harness.py` — see "Harnesses" above) because `KSession::setEnvironment` is not QML-reachable; `focus_agent`/`cycle_agent_focus`/`close_agent` (refocuses the previous chip in display order, or the next if none exists); `on_agent_finished`/`on_agent_title` QML callbacks). `centralSurface` gained `"agent"` via the validating `set_central_surface` primitive. `_on_bridge_snapshot` mirrors activity for ids prefixed `f"{os.getpid()}_"` — hook-driven sparkle animation arrives THROUGH the bridge, never directly.
3. **QML agent surface** (Main.qml): a FIXED `Repeater { model: controller.maxAgentSlots }` of per-slot Loaders → `QMLTermWidget`+`QMLTermSession` on the shared rendering contract. Loader activation = spawn; deactivation = close (the KSession destructor reaps claude — verified no orphans). **Do NOT convert to a list-model Repeater** — delegate churn kills live claude processes. `AgentTopBar.qml` renders the bubbles via the shared `Symmetria.Agents.UI` module (installed at `/usr/lib/qt6/qml/Symmetria/Agents/UI` from `~/projects/symmetria-agents-ui`; dev override `SYMMETRIA_IDE_AGENTS_QML_PATH`). `AgentTopBar.qml` also carries the terminal/editor/agents surface switcher at its left edge (moved from StatusBar's center 2026-06-11; centering/anchoring rationale lives in AgentTopBar.qml's comments).

**Why hooks Just Work:** the spawn argv exports `SYMMETRIA_AGENT_ID=<ide_pid>_<slot>`, which matches the bridge's `f"{nvim_pid}_{buf}"` keying for our published instances — Claude's hooks (`symmetria-agent-hook.py`) report activity to the bridge under that id, the bridge folds it into snapshots, and the subscription feed drives both the IDE's bubbles and the shell dashboard identically. (⚠ Under CC 2.1.x's daemon spare-pool this env id is no longer trustworthy for attribution — see the Daemon caveat below; the reliable keys are now `session_id`+`cwd`.)

**⚠ Daemon caveat (Claude Code 2.1.x) — the env `agent_id` is NO LONGER authoritative for attribution.** CC's per-user daemon + pre-warmed spare pool freezes `SYMMETRIA_AGENT_ID`/`SYMMETRIA_IDE_AGENT_SOCK` to the pool creator and reuses them across projects, so an agent's events report to the wrong IDE under the wrong id (sparkle desync: idle agent shows working, working shows idle). Fixed (dev, 2026-07-04; needs stable promotion to reach the daily driver) by attributing on the surviving signals — the hook's `session_id` + real `os.getcwd()` — via `src/symmetria_ide/agent_registry.py` (reporter self-routes to the owning IDE; `_on_agent_hook` resolves the slot from session+cwd, not the frozen id). Mechanism + the status-line-tap follow-up: `.claude/memory/reference/agent-sdk/daemon_freezes_agent_env.md`.

**Smoke hook:** `SYMMETRIA_IDE_SPAWN_AGENT=fresh|resume|continue` spawns one agent at launch, with an optional `:<harness>` suffix (`fresh:opencode`) — E2E flow in `docs/dev-workflow.md`. Claude resume carries no session id by design — claude's own interactive `-r` picker is the resume UX. OpenCode resume instead routes through the IDE's AgentSessionPicker (it needs an explicit `--session` id).

**Worktree follow (shipped 2026-07-13).** When the FOCUSED agent's live work location sits inside a **linked git worktree of the same repo**, the chrome (tree + all git surfaces) re-roots to that worktree. ⚠ The load-bearing signal is the **WRITE-tool target path**, not the session cwd: an agent working in a worktree via Bash/absolute paths NEVER moves its session `os.getcwd()` (a Bash-tool `cd` changes the tool's persistent shell only, not the session cwd), so the reporter forwards each hook's `tool_input.file_path`/`notebook_path` as `tool_path`, and the IDE stores `resolve_project_root(tool_path)` into the slot's `work_root` gated on `_AGENT_WRITE_TOOLS` (Edit/Write/MultiEdit/NotebookEdit — Read/Grep deliberately excluded so exploration never yanks the chrome; last write wins, so editing main pulls back). Mechanics + invariants: every hook's `payload["cwd"]` is also captured into `live_cwd` (fallback signal — only moves if the session itself was spawned elsewhere); NEITHER field ever overwrites the spawn-time `cwd` (slot attribution, the bridge project label, and tmux naming derive from it); `_recompute_agent_root_override` (app.py) is the SINGLE funnel deriving `_agent_root_override`, the third and highest-precedence `displayedRoot` source (override > anchor > cwd; the anchor stays latent underneath and reasserts when the follow clears). Follow-on-focus, sticky-until-re-caused: surface swaps and shell/nvim `cd` never snap back (the `_route_capsule` cwd gate covers the override like the anchor); it moves only on focusing a differently-rooted agent, the focused agent cd-ing out (next hook), or the pool emptying. Detection is pure (`worktree.py`: `.git` POINTER-FILE parse, target `…/.git/worktrees/<name>` — submodules' `.git/modules/` rejected; no subprocess). Foreign repos / non-repo roots CLEAR the follow (v1 scope); VPS contexts are left untouched (the funnel's vps guard also prevents re-entering `_switch_location` via displayedRootChanged→`_reprobe_vps_pairing` mid-toggle). **New agents ALWAYS spawn in the MAIN checkout** (user decision 2026-07-13, reversing the first-cut "everything follows" spawn): `spawn_agent` redirects a worktree `displayedRoot` (follow-driven OR manual cd/anchor) to `linked_worktree_info(...)`'s main root — narrow on purpose, plain subdirs keep their cwd; spawning while following therefore also RETURNS the chrome to main (the new agent gets focus). Ctrl+1..5 while the spawn menu is open dismiss it and navigate (the menu is exempt from the modal guard, same idiom as Ctrl+Shift+A — an unexempted guard left Ctrl+1..5 dead until Esc). ⚠ The branch glyph lives in `Theme.glyph.worktree` (both QML sites bind the token) as the ESCAPE `"\uf418"`, never the literal PUA character — a literal once arrived as an empty string through an edit pipeline and rendered as nothing (invisible glyph, zero warnings). Registry consequence (load-bearing): `_sync_agent_registry` publishes the CANONICAL main root as `project_root` plus a `roots` list (main + each local agent's resolved root) so first-event hook routing survives re-rooting, and `resolve_slot_for_event` compares canonical roots so same-repo worktrees count as one project. Indicators: branch glyph on the agent chip (`agentWorktree` per-slot name list, dedicated `agentWorktreeChanged` notify — deliberately not `termAgentsChanged`) and beside the tree header's root label (`displayingWorktree`). ## The agent backend (Node SDK sidecar — PARKED, env-gated)

Distinct from the capsule / completion / which-key pipelines above — this one connects our Python backend to the official `@anthropic-ai/claude-agent-sdk` running in a Node sidecar process. **Parked and env-gated since the terminal-agent runtime shipped: the AgentPane only mounts when `legacySdkPaneEnabled` is true (`SYMMETRIA_IDE_SDK_PANE=1`, implied by `SYMMETRIA_IDE_AGENT_PROMPT`/`_VIEW`).** It is a different bet (structured chat with in-pane permission cards vs terminal TUI) kept for a future revisit. We pivoted away from `claude -p --output-format stream-json` CLI scraping because that mode self-resolves permissions server-side and exposes no in-band approve/deny surface. The SDK's `canUseTool` callback gives us a structured permission request as a typed async function — the same path Zed's `claude-code-acp`, opencode, and the official VS Code extension take.

**Topology.** `SessionHost.start(prompt)` spawns `node sidecar/dist/index.js` with stdin/stdout/stderr piped. The sidecar (`sidecar/src/index.ts`) runs `query({ prompt: <async iterable>, options: { canUseTool, includePartialMessages: true, permissionMode: "default" } })` and translates SDK messages to JSONL events on stdout. Python's daemon stdout worker iterates `proc.stdout.readline()`, parses each line via `parse_stream_json_line`, and emits `event_received(dict)` onto the GUI thread via `Qt.QueuedConnection`. A second daemon reads stderr and emits `stderr_line(str)`; `AppController._log_session_stderr` forwards those to the app log.

**Pool topology (Phase A — multi-instance plumbing).** `AppController` owns slot-keyed dicts (`_session_hosts: dict[int, SessionHost]`, parallel `_session_models`, `_awaiting_response`, `_permission_mode`) instead of singular fields. Phase A allocates only slot 1 — single-instance behavior is preserved — but every dispatch path is index-aware. The QML pane reads `controller.awaitingResponse` / `controller.permissionMode`, both of which now read from `_focused_instance`'s slot in those dicts. New indexed slots (`focus_instance(int)`, `cycle_permission_mode_for(int)`, `submit_prompt_for(str, int)`, `respond_to_permission_for(str, str, int)`) accept an explicit slot; nullary wrappers route to `_focused_instance` and remain the QML-facing surface. `_create_instance(slot)` allocates one pool entry — its constructor wires every host signal via `lambda event, idx=slot: …` (default-arg capture is load-bearing — Phase B's cascade-spawn would otherwise misroute every event to the last slot allocated). Per-instance signal-emit gate: `_set_awaiting_response_for` / `_set_permission_mode_for` mutate the slot's dict entry unconditionally but emit the QML-facing `*Changed` signal ONLY when `slot == _focused_instance`, so non-focused activity doesn't flicker the focused pane. Permission responses route via `_pending_permissions: dict[str, int]` (request_id → issuing slot) — never via `_focused_instance` — so a focus-switch between request and response still delivers the user's decision to the correct sidecar's canUseTool promise. AgentPane.qml shows `<focused> / <total>` beside the pillHint — no per-instance colours per PRD §3.2 (the Symmetria Shell dashboard owns colour assignment, indexed by slot number sent in `color_idx`). See `docs/orchestrator-replacement-prd.md` Phases B–G for the keybinds + spawn semantics + bridge emitter that build on this foundation (shelved; Phases B–G are deferred).

**Pre-warm.** The sidecar is **pre-warmed at IDE launch** by `AppController.start()` calling `self._session_hosts[1].start("")` — empty prompt spawns the subprocess but skips the initial `send_user_message`, so the SDK's prompt async iterable blocks on its first await until the user types in the composer. This pre-warm is what makes the permission-mode pill render correctly and Shift+Tab cycle the moment the agent pane is visible — without it, `set_permission_mode` writes silently dropped on a non-existent stdin until the first user message, leaving the user assuming the binding is broken. The `SYMMETRIA_IDE_AGENT_PROMPT` env-var path still pre-runs an initial turn but flows through the already-warmed-subprocess path inside `submit_prompt` (`send_user_message` on the already-pre-warmed subprocess); the synthetic user-row optimistic injection still renders the prompt without waiting for an SDK echo.

**Build artifact.** The sidecar's `dist/index.js` is gitignored — `npm run build` in `sidecar/` regenerates it via esbuild (SDK marked `external` so its native binary opt-deps resolve from `node_modules` at runtime, not bundled). Requires Node `>=20`. `SessionHost.start` checks `_sidecar_dist_path()` exists before spawning and surfaces a clear log error pointing at `cd sidecar && npm install && npm run build` if missing.

**Wire protocol.** Defined in `sidecar/src/protocol.ts`; mirrored in `session_host.py`'s module docstring. Inbound (Python → sidecar):

```
{"type": "user_message", "content": "..."}
{"type": "permission_response", "request_id": "<uuid>",
 "behavior": "allow" | "deny", "message"?: "..."}
{"type": "set_permission_mode",
 "mode": "default" | "acceptEdits" | "bypassPermissions" | "plan"}
```

Outbound (sidecar → Python): SDK messages translated to JSONL events. The sidecar **drops `SDKUserMessage` echoes entirely** — Python's optimistic-render in `submit_prompt` (the synthetic user-row injection) is the single source of truth for user-row rendering; re-emitting the SDK echo would duplicate every user turn. Do NOT remove the synthetic injection when refactoring `submit_prompt`. The new `permission_request` envelope is sidecar-synthesized when `canUseTool` fires:

```
{"type": "permission_request",
 "request_id": "<uuid>",
 "tool_name": "Bash" | "Read" | ...,
 "tool_use_id": "<uuid>",
 "input": {...},
 "title"?, "description"?, "display_name"?, "blocked_path"?, "decision_reason"?,
 "note": "sidecar-synthesized"}
```

The matching Python-side reply must echo the same `request_id`. The sidecar holds a `Map<request_id, resolver>` and resolves the awaited `Promise<PermissionResult>` when the response arrives. SDK aborts (session shutdown, query cancellation) auto-resolve pending entries with `{behavior:"deny", interrupt:true}`.

Top-level outbound `type` discriminators that `SessionModel.apply` routes (other types fall through to an empty-role visible row so new envelopes surface during exploration):

| type                | payload shape                             | `SessionModel` row treatment                                  |
|---------------------|-------------------------------------------|---------------------------------------------------------------|
| `system`            | `subtype` ∈ {init, hook_*, compact_boundary, …} (`"status"` keepalives filtered at sidecar, never reach here) | role=`system`, text summarises subtype |
| `stream_event`      | nested `event.type` (SSE frame)           | only `content_block_delta.text_delta` extends the streaming row |
| `assistant`         | `message.content[]` (text + tool_use)     | role=`assistant`, tool_use blocks render as `[tool: <name>]`  |
| `user`              | dual-mode by content shape (see below)     | text-only echoes dropped at sidecar; tool_result-bearing envelopes become `kind="tool_result"`, `role="tool"` rows via `_row_from_user` |
| `result`            | `duration_ms`, `total_cost_usd`, …        | role=`system`, "done · Nms · $X"                               |
| `rate_limit_event`  | `rate_limit_info.{status,rateLimitType}`  | role=`system`, dim info row                                    |
| `permission_request`| sidecar-synthesized (see shape above)      | `kind="permission_request"`, `permission_state="pending"`, drives the QML approve/deny card |
| `permission_mode_changed` | sidecar-synthesized; `{mode: "default"|"acceptEdits"|"bypassPermissions"|"plan"}` | NOT routed by `SessionModel`; `AppController._on_session_event` mirrors into `_permission_mode` for the QML pill |
| anything else       | —                                         | empty-role row with kind as prefix                            |

Partial coalescing: when a `stream_event.content_block_delta` with `delta.type == "text_delta"` arrives, `SessionModel` extends the most recent streaming row's text via `dataclasses.replace` + list swap, and emits `dataChanged` with an explicit role list scoped to `TextRole` (gotcha #3 — empty role lists force full re-bind; scoped lists let QML re-evaluate only the changed binding). Any non-stream-event event resets the coalesce index so the next `text_delta` opens a fresh row.

Tool-result protocol: Anthropic overloads the `user` role for two semantically distinct things — fresh human turns AND tool_result blocks fed back to the model. The sidecar disambiguates by content shape via `containsToolResult` (`sidecar/src/index.ts`): a `user` envelope whose content is purely text is type (a) and gets dropped to preserve Python's optimistic-render contract for user-prompt rows; an envelope carrying any `tool_result` block is type (b) and passes through. On the Python side, `_row_from_user` calls `_extract_tool_result_blocks` first — non-empty result becomes `kind="tool_result"`, `role="tool"`, body flattened via `_flatten_tool_results` (string content verbatim; nested content blocks via `_flatten_content_blocks`; multiple blocks joined with blank lines), with `subtype="error"` when any block carries `is_error: true`. AgentPane.qml's `_formatRoleLabel` renders these as `"Tool result"` (or `"Tool · error"`) and borrows `text.dim` for both label and body — same rationale as system rows: machine output stays quieter than user/assistant turns. The text-only fallback path in `_row_from_user` is defensive — if a future SDK change leaks a text-only `user` envelope through the sidecar filter, it renders as a user echo rather than crashing.

Permission flow: a `permission_request` event lands in `SessionModel` as a row with `permission_state="pending"` + `request_id`. `AgentPane.qml`'s delegate variant renders an inline approve/deny card whose buttons call `controller.respond_to_permission(entry.requestId, "allow"|"deny")`. `AppController.respond_to_permission` writes the `permission_response` to the sidecar (host first — its promise resolves before our UI feedback fires) then mutates the model row to `"approved"`/`"denied"` via `resolve_permission`, which emits a scoped `dataChanged([PermissionStateRole])`. The `awaitingResponse` spinner stays ON during a pending permission — the turn is still in flight from the user's perspective; only the SDK's `result` envelope flips it OFF.

Permission mode flow: the agent pane's chrome bar carries a Theme-tokened pill bound to `controller.permissionMode`. Shift+Tab on the pane (root or composer) cycles `default → acceptEdits → bypassPermissions → plan → default` via `AppController.cycle_permission_mode()`, which dispatches `set_permission_mode` to the sidecar. The **sidecar's local `currentMode` is the authoritative source of truth** for permission gating — `canUseTool` reads it directly to decide auto-allow / auto-deny / round-trip. On receipt of a `set_permission_mode` command the sidecar updates `currentMode` synchronously and emits the `permission_mode_changed` echo immediately; `AppController._on_session_event` mirrors the echo into `_permission_mode` so the QML pill reflects what the sidecar already accepted. A best-effort `Query.setPermissionMode()` call is also fired so the SDK's server-side mode awareness tracks the local one — this push is async and never blocks the echo (see gotcha #25 for why it cannot be the source of truth). The sidecar's `canUseTool` callback short-circuits per mode: `bypassPermissions` auto-allows everything (echoes `input` as `updatedInput` per gotcha #24), `plan` auto-denies everything, `acceptEdits` auto-allows the four edit tools (`Edit`/`Write`/`MultiEdit`/`NotebookEdit`), `default` (and `acceptEdits` for non-edit tools like `Bash`/`Read`/`Grep`) round-trips through the in-pane card. Auto-resolved cases do NOT emit a `permission_request` envelope, so the QML card is correctly suppressed for the modes that bypass it. `_on_session_closed` resets `_permission_mode` to `default` so the pill doesn't lie about a dead subprocess's last mode.

The sidecar also filters `{type: "system", subtype: "status"}` keepalive messages at `translateMessage` so they never cross the wire — without that filter the Python-side `_row_from_system` falls back to `text = subtype` and renders a continuous stream of "status / status" rows that drown out real session events. New `system` subtypes still pass through (per the placeholder discipline of letting unknown envelopes surface during exploration); only the known-noise `"status"` value is dropped.

Thread safety:
- `SessionHost._run_stdout_loop` suspends GC around the emit (gotcha #10 — Python 3.14 cyclic GC racing `QSGRenderThread` is the same class of SEGV the deleted nvim render worker solved via the same pattern).
- The cross-thread `event_received → SessionModel.apply` and `event_received → _on_session_event` connects use explicit `Qt.QueuedConnection` per project-standards §4 P2, with a one-line grep-able comment at the connect site.
- `_stop_event` + daemon workers satisfy project-standards §1 P0 ("every long-running thread is daemon=True OR owns an explicit shutdown Event"). We satisfy both, matching `NvimBackend`.

SDK version pin: `@anthropic-ai/claude-agent-sdk@0.2.119`. The pin is exact (no caret) so behaviour is reproducible — security patches require a manual bump. Authentication uses the same `~/.claude` credentials as the CLI; the SDK reads them at `query()` time. Turn grouping + tool-call drill-in are still deferred — the SDK exposes far richer event vocabulary than `-p` did, but the placeholder discipline (`.claude/memory/ui_surface_discipline.md`) means we ship the structural surface first and iterate the visual treatment once real cadence is observable.

## The location toggle (Local ↔ VPS — shipped 2026-07-12)

One project window, two execution locations: `AppController._location ∈ {"local","vps"}`, orthogonal to the anchor AND to `centralSurface`, flipped by **Ctrl+Shift+U** / the AgentTopBar `local|vps` segments. In the vps location, agents/tree/git/terminal all operate on the paired server's repo — the same Vigilia stack the phone (the Vigilia mobile app) drives (see `~/projects/vigilia/docs/convergence-architecture.md`; this feature is its desktop half). Non-derivable invariants:

- **Pairing is by repo identity** (displayedRoot basename exists as a git repo under a registered server's `repos_dir`), probed async on every root change; location force-resets to local on project switch and pairing loss. No per-project config.
- **Every ssh argv comes from `ssh_runner`** (identity pinning is the fail2ban guard from Vigilia's first live bootstrap; ControlMaster multiplexing is what makes per-scan remote git affordable). The ONE deliberate exception: sshfs owns its own connection — `-o reconnect` through a shared master would wedge the FUSE mount when the master dies, and `ssh -O exit` at shutdown would yank the filesystem from under FUSE.
- **VPS agents are tmux attaches, not migrations**: `ssh -t → tmux -S /home/dev/.vigilia/tmux.sock new -A -s <repo>-vps-<slot>` (or an existing session via the spawn menu's `a` picker). Ctrl+Shift+Q DETACHES (session lives on, phone keeps it); **Ctrl+Shift+K + confirm** is the explicit remote kill. `on_agent_finished` for a vps slot is the SSH CLIENT exiting, never agent death — no OOM heuristics. VPS records are NOT published to the shell bridge/registry (the server's `agent_hub.py` owns their identity, keyed by tmux session name); their inner argv carries NO env wrapper / reporter / MCP config (Vigilia manages the server agent env), only dangerous/spawn-type/model/effort flags.
- **The pool is one physical slot namespace, location-filtered views**: `agentOrder`/cycling/refocus/display numbers filter via `_ordered_slots_for_location`; `agentSlotActive` stays location-BLIND so the other location's Loaders never churn (churn kills live panes). Invariant: `focusedAgent` is 0 or a current-location slot (focus_agent location-follows; `_switch_location` hands focus off via `_focused_by_location`).
- **Sparkles for vps agents ride the forwarded hub**: `SocketForward` (`ssh -N -L`) + a second `AgentBridgeClient` → `_on_hub_snapshot`, mapping `agents[].id` = tmux session name → slot. `_on_hub_snapshot` and `_on_bridge_snapshot` rebuild DISJOINT slot sets — each carries the other's entries through; breaking that wipes sparkles on whichever feed lags.
- **Remote chrome = SSHFS for the tree, ssh-executed git for data**: `GitController.set_remote` pins `_resolved_root` to the MOUNTPOINT (that one assignment is the whole path translation — porcelain rel-paths join onto it, so every published path stays local) while git runs `git -C <remote_root>` on the server; rev-parse is skipped; both watchers stand down (inotify is blind across SSHFS) and a 5s `_remote_poll` drives the debounce funnel. Log/branch/ops swap to a shared frozen `git_subprocess.GitExecutor` (pull/push run on the SERVER with its credentials); the PR tab deliberately never switches (gh talks to GitHub; both checkouts share the origin).
- **The terminal surface is two panes** (local shell / remote `ssh -t` login shell), one visible per location; the remote pane has NO cwd-poll Timer (its `currentDir` is the local ssh process — feeding it to `on_shell_cwd` corrupts the anchor); focus terminal panes ONLY via Main.qml's `_focusTerminalPane()` — a direct `forceActiveFocus()` on `terminalView` targets the wrong pane in vps.
- Smoke: `SYMMETRIA_IDE_SPAWN_AGENT=fresh SYMMETRIA_IDE_SPAWN_AGENT_LOCATION=vps` defers the spawn to the pairing edge (full E2E in `docs/dev-workflow.md`).
- v1 deferrals (deliberate): coordination (`wait_for_agent`) is local-only and refuses vps chips; no reconnect chip state (an ssh drop closes the slot with a toast); no mosh; no auto-clone of a missing remote repo; the tree header above the changes panel still shows the LOCAL compact root in vps.

## The terminal panes (editor nvim + shell)

Both central surfaces — the **editor** (`nvim --listen` as a TUI) and the **shell** — are `QMLTermWidget` items from our fork of qmltermwidget (Konsole's VT engine + renderer as a QML element, what cool-retro-term uses). They coexist under `Main.qml`'s `mainContent` Item; one of editor/terminal/agent/git/browser/FM is visible at a time (`editorVisible`/`terminalVisible`/`agentVisible`/`gitVisible`/`browserSurfaceVisible`/`fmVisible`, all derived from `controller.centralSurface`). The browser surface is `qml/BrowserSurface.qml` — see "The browser panes" below. First-launch visible = terminal (terminal-first topology; see `docs/future.md` "Topology inversion"). The earlier pyte-based renderer (`terminal_backend.py`/`terminal_view.py`/`terminal_keys.py` + `term_repl.py` + `runtime/symmetria-shell/`) was deleted in the qmltermwidget migration — do not look for it.

**The fork.** Lives at `/home/jc/projects/symmetria-qmltermwidget` (branch `symmetria`, off upstream `ce8e09a`), GPL-2.0-or-later. See its `MODIFICATIONS.md` for the three upstream defects it fixes — all to make background transparency reachable: (1) `ColorScheme::read` used `beginGroup("General")` which QSettings never matches for an INI `[General]` section, so `Opacity` was silently defaulted; (2) `setColorScheme` never applied the scheme's parsed opacity; (3) `setOpacity` wasn't QML-reachable. The fork adds a `backgroundOpacity` `Q_PROPERTY` (named NOT `opacity`, which is `QQuickItem`'s own render-opacity that fades text too) and ships the `Symmetria` colorscheme.

**Import path.** Three-way resolution on `SYMMETRIA_IDE_QMLTERMWIDGET_PATH`: *unset* → `_build_engine` adds the hardcoded checkout dir (`/home/jc/projects/symmetria-qmltermwidget`) to the import path (repo-run default, useful for pre-install fork iteration); *empty* → no `addImportPath`, `import QMLTermWidget 2.0` resolves from the installed `symmetria-qmltermwidget` pacman package at `/usr/lib/qt6/qml` (what BOTH launchers set — the production path); *set to a dir* → that dir. Unset-vs-empty matters: repo smoke runs exercise the checkout build and pass while the launcher path is broken by an un-packaged fork change — the engine fails to load on whatever property/type the installed package doesn't ship yet (fix: `makepkg -sif` in the fork's `packaging/`; full procedure in "Runtime deps" above). Build the checkout with `qmake6 && make -j$(nproc)` → `QMLTermWidget/{libqmltermwidget.so, qmldir, color-schemes/}` — needed for the *unset* (checkout-iteration) case only; the pacman-package path requires no manual build.

**Transparency invariants (all three required).** `useFBORendering: false` (the FBO render path has no alpha → opaque; the image path is still C++-fast) + `fillColor: "transparent"` + `colorScheme: "Symmetria"` (applies the scheme's 0.6 background opacity) + the Window root `color: "transparent"` (+ the `QSurfaceFormat` alpha-buffer request in `run()`). Retune opacity live via the `backgroundOpacity` property — no rebuild needed.

**ANSI palette.** The fork's `Symmetria.colorscheme` (16 colors + bg/fg) mirrors `Theme.color.terminal.*` in `qml/design/Theme.qml`. It is committed in the fork's `lib/color-schemes/` and copied to the build-output `QMLTermWidget/color-schemes/` (gitignored) at build time. The build-output copy is the one loaded — a spike's runtime regenerator once clobbered it (dropped `[BackgroundIntense]`); if you see an `Invalid color value "" for "BackgroundIntense"` warning, re-copy from `lib/`.

**Editor nvim launch + the RPC seam.** The editor's `QMLTermSession` spawns `nvim` (`shellProgram: editorProgram`, `shellProgramArgs: editorArgs` context props built in `_build_engine`) with `--listen <socket>` + the runtime injection. nvim draws its grid in the widget; the Python `NvimBackend` attaches an RPC-only client to that socket for the chrome relays (cmdline/which-key/capsules/completions/minimap) + control (`input`/`edit_file`/`set_current_dir`). **This relay is the IDE's signature and is INDEPENDENT of the terminal renderer** — it survived the pyte→qmltermwidget swap untouched. Because the QMLTermSession starts in `Component.onCompleted` (during `engine.load`, before `controller.start()`), nvim is usually already binding its socket by the time `NvimBackend.start()` attaches; the attach still polls with a retry budget on the worker thread.

**Shell launch + cwd sync.** The shell's `QMLTermSession` runs `$SHELL` (`shellExec`/`shellExecArgs` context props — named to avoid colliding with QMLTermSession's own `shellProgram`/`shellProgramArgs`) as a plain interactive shell, reading the user's real `~/.zshrc`/`~/.bashrc` (the old OSC 7 rcfile/ZDOTDIR injection is gone). cwd sync: `QMLTermSession.currentDir` is tracked natively by Konsole (foreground process cwd via `/proc`), but has **no change signal** — a 600ms `Timer` in Main.qml polls it and forwards changes to `controller.on_shell_cwd`, which routes through the same `_route_capsule({id:"cwd"})` path nvim's `:cd` uses (anchor state machine + file tree + git controller all see it through their existing wires).

**`QMLTermSession` is not Python-wrappable.** It's a `KSession*`; `obj.property("session")` from PySide raises "Can't find converter". Drive it entirely from QML (`startShellProgram()` in `Component.onCompleted`, `currentDir`, `onFinished`).

**Lifecycle.** Both sessions spawn in QML `Component.onCompleted`. `shutdown()` calls `_backend.stop()` (graceful `qa!` over the socket so nvim writes shada/swap cleanly); the KSessions reap their child processes when the QML engine tears down on app quit — there is no Python-side killpg backstop anymore. The editor session's `onFinished` calls `Qt.quit()` (nvim `:qa` closes the IDE), redundant with the existing `backend.closed → app.quit` wire (both idempotent). The shell session's `onFinished` is log-only in v1 (a dead shell pane stays until the user swaps).

**Chords.** All IDE chords are `Qt.ApplicationShortcut` at the Window root and win over the terminal's key handling (verified live). **Surface-swap chords share a swap-last-two / alt-tab model (shipped 2026-06-21):** a single `_previous_surface` pointer is recorded at the one funnel `AppController.set_central_surface` (so it tracks EVERY transition — chord, `focus_agent`/`open_browser` auto-switch, top-bar switcher, file-open), and `_surface_back_target()` (= that pointer, falling back to terminal only when there's no history) is the "return" direction for every surface chord. So each chord is symmetric: pressing it from elsewhere goes **forward** to its named surface; pressing it while already there goes **back** to wherever you came from — no surface is a privileged forced-fallback for the *return* direction anymore (terminal stays the fallback only at cold-start before any history is recorded, on a self-return, or when the recorded surface is an emptied agent/browser pool — `_surface_is_navigable`). The lone exception is the agent chord (`Ctrl+Shift+A`), which on the agent surface opens the spawn menu rather than swapping back (spawning another agent is the more common intent there than returning to the previous surface). Concretely: `Ctrl+Shift+E` editor toggle (`toggle_editor_terminal` — non-editor → editor, editor → back), `Ctrl+Shift+T` terminal toggle (`toggle_terminal_home` — non-terminal → terminal, terminal → back; `swap_to_terminal` survives as the one-way "go home, no bounce" primitive for file-open/tests; the chord was briefly retired as redundant with Ctrl+Shift+E back when the IDE had only editor+terminal, re-added 2026-06-16, and the swap-last-two model now makes it a genuine toggle rather than a duplicate — don't re-retire it), `Ctrl+Shift+P` anchor (was Ctrl+Shift+A until 2026-06-10 — A now belongs to the agent namespace), `Ctrl+Shift+G` git-history toggle (`toggle_git_history` — non-git → git, git → back; ## The browser panes (agentic browser — Phase 4 Stage 1)

Embedded QtWebEngine `WebEngineView`s on the `"browser"` central surface (`qml/BrowserSurface.qml`), shipped 2026-06-16 as Stage 1 of the pulled-forward Phase 4 (`docs/phases.md`). **Containment principle (load-bearing — write it down so nobody reaches for an X11-style window-grab Wayland forbids):** an agent-spawned external browser escapes into Hyprland because it creates a top-level OS window; embedding the engine as a QML *item* renders it into the IDE's own window, so the compositor never sees a second window. On Wayland there is no reparenting/window-grab, so embedding (or headless+screencast) is the only path.

## The which-key protocol

Lua emits `vim.rpcnotify(0, "whichkey", payload)` where payload is:

```
{ op = "show" | "hide",
  mode = "n",
  trail = "<leader>" | " b" | ...,  -- accumulated path from root
  can_go_back = bool,                -- true iff <BS> should pop to parent
  items = {                          -- only on "show"
    { key = "b", desc = "Buffer navigation", is_group = true,
      icon = "", icon_color = "#b4b4b4" },
    ...
  } }
```

Python routes to `WhichKeyState` (visibility + trail + canGoBack) and `WhichKeyModel` (`QAbstractListModel` with roles key/desc/isGroup/icon/iconColor). Both connect to the same `whichkey_event` signal on `NvimBackend` — each ignores payloads it doesn't care about.

The **data source for items** is the union of (in this order, earliest wins the desc upsert, latest wins rhs/callback):

1. **Preset catalog** — `which-key.nvim`'s hand-curated `plugins/presets.lua` (loaded lazily, memoized) contributes descriptions for built-in nvim motions that `nvim_get_keymap` doesn't return: `gg`, `gU`, `gf`, `zz`, `[s`, `<C-w>h`, etc. Single-char motions (`h`, `j`, `k`, `l`, `w`, etc.) are filtered out — they're direct motions, not menu content.
2. **`vim.api.nvim_get_keymap(mode)`** — user-defined global keymaps.
3. **`vim.api.nvim_buf_get_keymap(0, mode)`** — buffer-local keymaps (LSP, treesitter, etc.). Shadows globals.

The trie is rebuilt on `BufEnter`, `LspAttach`, `LspDetach`, and once on `VimEnter`. Triggers are installed only for top-level trie prefixes that are groups AND don't clash with a user's real keymap (`user_has_real_mapping` skips anything with a non-empty rhs or a callback).

## Non-obvious gotchas (burned in Phase 0, don't relearn)

1. **pynvim is not thread-safe.** Any RPC call from the Qt GUI thread raises `NvimError: request from non-main thread`. Always marshal through `nvim.async_call`.
2. **Subscribe race.** `init.lua` runs during nvim startup and fires its initial capsule push *before* Python subscribes to the `"capsule"` notification. Python must actively re-request the push (via `exec_lua("_G.symmetria_push_state()")`) after subscribing, or the status bar stays empty until the first mode change.
3. **QML non-bindable function calls don't re-evaluate.** `Text.text: root.capsules.rowCount()` computes once and stays stale. Use role data inside a `Repeater` delegate, or bind to a property with a notify signal. This is why well-known capsules live on `StatusBarState` (per-field `@Property` with `notify=`) rather than in `CapsuleModel`.
4. **Window app_id** is set via `QGuiApplication.setDesktopFileName("symmetria-ide")` — this becomes the Hyprland window class, so `windowrule = workspace 6 silent, class:^(symmetria-ide)$` matches.
5. **Lualine will clobber `laststatus`.** Plugins set their own status-line config during `setup()`. Setting `laststatus=0` via `--cmd` is NOT enough — plugin setup runs after and wins. Re-set from a `VimEnter` autocmd to have the last word.
6. **Notification daemon on this system is Symmetria Shell (QuickShell), not swaync/mako.** `swaync-client` and `makoctl` are no-ops here.
7. **Pyright noise is not a bug.** PySide6 stubs mis-type `QAbstractItemModel.data`/`rowCount`/`roleNames` parameters, flag `@property` + `@QmlElement` decorators, and can't resolve relative imports without a `pyrightconfig`. Runtime works. Don't try to "fix" these by changing signatures to match the stubs — that breaks Qt's metaobject system.
8. **Plugins that also claim `ext_cmdline`/`ext_popupmenu` will conflict.** `noice.nvim` is the common case: it tries to draw its own cmdline overlay, notices an external GUI already claimed the extension, and echoes a warning into the grid every time the cmdline opens. `runtime/init.lua` sets `vim.g.symmetria_ide = 1` as a detection flag so the user's config can disable noice's cmdline/popupmenu modules conditionally (pattern borrowed from `g:goneovim`). Same applies to any future plugin consuming these ext flags.
9. **`cmdline_show` arg count varies by NeoVim version.** 0.9 sends 6 positional args (`content, pos, firstc, prompt, indent, level`); 0.10+ sends 7 (adds `hl_id` for firstchar). The backend handler accepts `_hl_id` with a default. Same forward-compat pattern (`*_rest: Any`) absorbs future additions on `cmdline_pos`, `cmdline_hide`, `popupmenu_show` without crashing.
10. **Python 3.14 cyclic GC will SEGV us if a worker thread allocates while the render thread is mid-`paint()`.** 3.14 tracks even tuples of primitives (regression vs 3.13) and runs incremental collections more aggressively. When the Qt `QSGRenderThread` is mid-`paint()` — inside a PySide6 → Qt C++ call like `painter.setPen(...)` — it's holding C++ pointers to Python-owned wrappers with the GIL released. If a worker thread simultaneously trips `gc.threshold` and runs a collection, the render thread's C++ access SEGVs. Mitigations that are live:
    - **Suspend GC around worker-thread signal emission.** `SessionHost._run_stdout_loop` (`session_host.py`) suspends GC around the cross-thread event emit — the same mitigation the (since-deleted) nvim render worker used in its redraw dispatch.
    - **Freeze long-lived state after startup** via `gc.freeze()` just before `app.exec()` inside `app.run()`, excluding Qt wrappers / QML engine / controller from every future collection.
    - **Never allocate a PySide6/shiboken wrapper inside `paint()`** — cache it, pool it, or mutate in place. The decisive historical fix was memoizing `QColor` in the deleted renderer's `_rgb_to_qcolor` (it allocated hundreds of fresh wrappers per frame); the same rule now governs `minimap_view.py`, the one surviving `QQuickPaintedItem` (gated off). `faulthandler.enable` is armed at import time in `__main__.py` and writes to `$XDG_STATE_HOME/symmetria-ide/crash.log`, so any relapse leaves a trace with the exact frame.
11. **(Retired — deleted editor renderer.)** Smooth-scroll spring geometry, formerly in `nvim_view.py`. See the consolidated note after #14.
12. **(Retired — deleted editor renderer.)** Cursor-animation delta spring (`CursorAnimation`), formerly in `nvim_view.py`. See the note after #14.
13. **(Retired — deleted editor renderer.)** Wall-clock cursor blink (`CursorBlink`), formerly in `nvim_view.py`. See the note after #14.
14. **(Retired — deleted editor renderer.)** Frame-driver gating over all animation sources, formerly in `nvim_view.py`. **Consolidated note for #11–#14:** the custom NeoVim grid renderer these four governed was **deleted in the qmltermwidget migration** — the editor now renders itself inside the `QMLTermWidget` (Konsole's VT engine owns scrolling, cursor, and blink). The numbers are kept as a deliberate gap so references to gotchas #15+ stay stable. If smooth-scroll / cursor animation is ever rebuilt (for the minimap, or a future own-editor core), recover the spring algorithms from git history (pre-qmltermwidget-migration commits).
15. **`vim.fn.getcharstr()` DEADLOCKS in the embedded nvim.** Which-key.nvim's state machine loops on `getcharstr()` (`state.lua:242-275`) — works fine in a TTY nvim where nvim owns the whole event loop, but in our embedded-nvim setup it holds nvim's main thread, preventing `rpcnotify` payloads from flushing to the Python UI client. Symptom: the first emit leaks through on initial show, then subsequent descent/emit never reaches Python, and eventually the Qt event loop on the Python side also stalls. **Rule for any future modal UI:** do NOT use synchronous `getcharstr` loops in Lua. Dispatch must go through nvim's keymap system (per-child ephemeral keymaps, like `orchestrator.whichkey.state`) or through autocmds so the main thread returns to the event loop between transitions.
16. **`vim.schedule` / `vim.defer_fn` don't fire during prefix-wait.** After a multi-key feedkeys like `"gg"`, nvim can end up in `timeoutlen` prefix-wait with chars still in typeahead. In that state, scheduled callbacks and timer callbacks queue up but DON'T execute until nvim reaches full safe-state — which may never happen until user input arrives. This burned us hard in early which-key iterations: `execute_leaf` uninstalled triggers, feedkeys-ed the keys, and tried to reinstall via schedule/defer — the reinstall never ran, leaving the trigger dead. **Never design a "feedkeys → cleanup" pattern that relies on scheduled callbacks.** Use synchronous mechanisms: `vim.cmd.normal` / `vim.cmd.normal!` executes the keys and returns before control leaves the current Lua call. No typeahead queue, no deferred cleanup, no race.
17. **Menu keymaps OVERWRITE triggers; `install()` must self-heal via `maparg`.** When `orchestrator.whichkey.state._install_for(g_node)` calls `vim.keymap.set("n", "g", ...)` to register the menu-child handler for the preset `gg → First line`, it REPLACES the trigger keymap at `g`. On menu close, `clear_menu_keymaps` deletes the menu keymap — and since the trigger was never re-installed, the `g` slot is now EMPTY. The next press of `g` dispatches nothing ("pressed gg → worked, then g → broken forever"). Fix stack: (a) `M.close()` calls `triggers.install("n")` after clearing menu keymaps; (b) `triggers.install()` does NOT trust its `_installed` cache — it verifies the actual keymap at each wanted slot via `vim.fn.maparg(keys, mode, false, true)` and reinstalls if our `TRIGGER_DESC` isn't present. The `_installed` cache lies after menu-overwrite; only `maparg` tells the truth.
18. **`nvim_get_keymap()` does NOT return NeoVim's built-in motion chains.** `gg`, `gu`, `gU`, `gf`, `ge`, `zz`, `zt`, `[s`, `]s`, `<C-w>h`, etc. are hardcoded in nvim C core — they're not keymaps at all, so they never appear in `nvim_get_keymap` output. A trie built purely from that API will show empty submenus under `g`, `z`, `[`, `]`, `<C-w>`. Which-key.nvim fills this gap by shipping a hand-curated preset catalog (`lua/which-key/plugins/presets.lua`). `orchestrator.whichkey.presets` loads that catalog and flattens it into our trie, filtering single-char motions (`h/j/k/l/w/b/e`) since those are direct motions, not menu content. The preset module is LAZY-LOADED by lazy.nvim (`event = "VeryLazy"`), so a `require` at very-early startup fails; we retry on each rebuild until we get a non-empty catalog and cache it. Observed: after certain `:edit` transitions the module becomes unloadable again — the cache is what keeps descriptions rich across buffer switches.
19. **Menu keymaps CLOBBER arbitrary plugin keymaps too — `clear_menu_keymaps` must save + restore via `mapset`.** Gotcha #17 fixed the case where menu-child keys collide with our own top-level triggers (the `g` as both prefix and `gg` child). But menu children also collide with THIRD-PARTY plugin keymaps at the same slot. Concrete case: flash.nvim binds global `s` / `S` to its jump callbacks; `gs` and `gS` appear in the which-key `g` preset, so opening the `g` menu installs menu keymaps at `s`/`S` that REPLACE flash's global maps. On menu close, deleting the menu keymap leaves those slots empty — the NEXT press of `s` anywhere in the buffer falls through to default vim `s` (= `cl`: delete char + enter insert). User symptom: "flash stopped working after I pressed some whichkey menu." Fix: `install_menu_key` captures `vim.fn.maparg(key, mode, false, true)` BEFORE replacing; `clear_menu_keymaps` calls `vim.fn.mapset(mode, false, saved)` to restore after `vim.keymap.del`. Two additional skips: (a) OUR OWN trigger keymaps (identified by `TRIGGER_DESC` in `desc`) — `triggers.install` already handles those slots; (b) buffer-local keymaps (`prev.buffer > 0`) — `vim.fn.mapset(mode, abbr, dict)` takes a mode + abbr + dict but does NOT honor `dict.buffer`; it would silently promote the buffer-local map to a global one, stomping keymaps in other buffers. Buffer-local keymaps are owned by LSP/treesitter and are reinstalled on the next `LspAttach`/`BufEnter`, so skipping them is safe. Any future menu keymap mechanism MUST preserve arbitrary prior keymaps, not just our own triggers — and MUST NOT attempt to restore buffer-local keymaps via `mapset`. `TRIGGER_DESC` is now defined in `constants.lua` (shared between `state.lua` and `triggers.lua`) — do not duplicate it as a string literal in either file.
20. **`nowait = true` is authoritative ONLY for buffer-local mappings.** Per `:h :map-<nowait>`, the flag suppresses the `timeoutlen` wait *only* when the short mapping is buffer-local and the longer ambiguity-creating mapping is global or in another scope. A GLOBAL mapping with `nowait = true` is silently ignored whenever a longer mapping exists anywhere — overwhelmingly the case in practice because LSP sets buffer-local `gd`/`gi`/`gr`/`gy`/`gD` on attach, plus plenty of plugins bind `gcc`, `gx`, etc. For the native which-key overlay this manifested as: (a) ~500–800ms latency between pressing the second key of a chord (e.g. the second `g` of `gg`) and the action firing, and (b) fast `gg` bypassing the menu entirely because nvim consumed both chars into the built-in `gg` motion during the timeout wait. Diagnosed via a since-removed `trace.lua` tracer — `Δ(T1 install_for DONE, T2 on_child_pressed)` was 503–780ms while `Δ(T0, T1)` and `Δ(T3, T4)` were sub-millisecond, pinpointing the delay to nvim's timeoutlen-wait on the second keypress. **Fix: both the trigger keymaps (`triggers.lua::install_one`) AND the menu keymaps (`state.lua::install_menu_key`) MUST pass `buffer = bufnr` alongside `nowait = true`.** The `_installed` cache is keyed on `"bufnr:mode:keys"` so per-buffer state survives correctly across buffer switches. Stale entries in unloaded buffers age out automatically — buffer-local keymaps die with their buffer. Triggers are reinstalled per-buffer by the existing BufEnter/LspAttach/LspDetach autocmd, which is the right lifecycle for buffer-local triggers. If a future refactor reverts either surface to `buffer = 0` (module-local) or drops the `buffer` param entirely, the latency bug returns instantly on any LSP-attached buffer.
21. **Autocmd registration order races the user's lazy-loaded LspAttach handlers — defer trie rebuild via `vim.schedule`.** Our orchestrator is loaded from `runtime/init.lua` during nvim startup, which registers our `BufEnter`/`LspAttach`/`LspDetach` autocmd VERY early. User plugins like `nvim-lspconfig` are typically lazy-loaded (`event = "BufReadPre"` / `"BufNewFile"`) and register their own `LspAttach` handlers much later, AFTER ours. When LSP attaches, autocmds fire in REGISTRATION order — ours first, user's second. If our handler rebuilds the trie synchronously, it reads `nvim_buf_get_keymap(0, "n")` BEFORE the user's handler has installed buffer-local keymaps like `gd`, `gD`, `gi`, `gt`, `gR` via `vim.keymap.set("n", "...", ..., { buffer = ev.buf })`. The buffer-local keymaps exist — we just read them one tick too early, so the submenu under `g` looks incomplete compared to real nvim. **Fix: wrap the rebuild + `Triggers.install` call in `vim.schedule(...)` inside the autocmd callback.** `vim.schedule` defers the work to the next event-loop tick, which is GUARANTEED to run after all synchronous handlers for the current event have fired, regardless of who registered first. Safe here because we're not in prefix-wait state (gotcha #16's concern); `LspAttach` is a regular autocmd dispatch, not a keypress-driven timeoutlen wait. If a future refactor "optimizes" away the `vim.schedule` as an unnecessary defer, LSP-installed keys silently disappear from the overlay on the very next LSP attach.
22. **`WinScrolled` delta is in LOGICAL lines; `display_rows_between` converts to DISPLAY rows before emitting.** *(Note: the Python-side consumer — `ScrollAnimation.shift`, `_rotate_scrollback`, `pos * ch` paint offset — was deleted with `nvim_view.py` in the qmltermwidget migration. The Lua-side principle below survives: `runtime/init.lua` still calls `display_rows_between` to convert before emitting the `"viewport"` notification, and the unit-mismatch hazard applies to any future Python consumer of that event.)* The scroll pipeline in `runtime/init.lua` originally emitted `delta = line('w0')_now - line('w0')_prev` — a logical-line count. With `wrap=off` and no folds, logical lines and display rows coincide and the bug is latent. With `wrap=on` on long-line buffers (the canonical case: CLAUDE.md with heavily-wrapped paragraphs), a single `j` can advance the topline by 1 logical line but shift the actual grid by many display rows — we observed 1:9 amplification during diagnosis. **Fix: `display_rows_between(prev, now, winwidth)` in `runtime/init.lua` converts before emitting.** It walks the range, handling closed folds as 1 row each and computing wrapped-line display count as `ceil(strdisplaywidth / winwidth)`. Drawbacks of the estimator: doesn't account for `'showbreak'` / `'breakindent'` / virtual text / extmarks — accurate to ±1 row per wrapped line in practice. **Do NOT remove or bypass `display_rows_between` in the WinScrolled handler**: the unit mismatch is silent on non-wrapped buffers and only surfaces on prose/markdown. Related: `ext_multigrid` + `win_viewport.scroll_delta` (what Neovide uses) would give display-row deltas natively, but that's a larger architectural shift for Phase 2+.

23. **QML `font.family` is single-valued; `font.families` (plural) does NOT exist on QML's font value type in Qt 6.11.** A comma-separated string like `"Iosevka, JetBrains Mono, monospace"` assigned to `font.family` is treated as ONE literal family name — not a CSS-style fallback list. QML therefore cannot do per-glyph cascade from the binding layer alone. The `editorFontFamily` context property (set in `_build_engine` in `app.py`) works around this: Python calls `default_font()` (in `editor_font.py`) once, which uses `QFont.setFamilies([primary, *fallbacks])` for the C++ cascade, then exposes the resolved primary family name as a single `str` context property. All three overlays (`StatusBar.qml`, `CommandLine.qml`, `WhichKeyOverlay.qml`) bind `font.family: editorFontFamily` — a single QString — so they track the same font the grid chose without drift. Do NOT reintroduce a comma-separated literal string in any QML `font.family` binding. Do NOT try to use `font.families: [...]` — it is not a property on the QML font value type. The canonical pitfall comment is in `qml/CommandLine.qml`.

24. **`PermissionResultAllow.updatedInput` is declaratively optional but functionally required.** `sdk.d.ts:1781` (within the `PermissionResult` allow variant at `:1779`, SDK v0.2.119 — line numbers shift across SDK bumps) types it as `updatedInput?: Record<string, unknown>` — every reasonable reader concludes it can be omitted on a vanilla "allow" path. The runtime is strict: the SDK's CLI control-protocol path (visible in `assistant.mjs` near the `permission response req=` log line) destructures `updatedInput` straight into the tool-invocation payload, and each tool's own Zod schema (Edit's `{file_path, old_string, new_string}`, Write's `{file_path, content}`, etc.) rejects `undefined` with a `ZodError`. Symptom: tool-using turns surface "permission system errored" or "ZodError on permission envelope" *after* the user clicks Allow; the failure is upstream of the user's decision, so a retry produces an identical error shape (this confused the assistant during diagnosis — it concluded the deny branch was missing a `message`, which it isn't). **Fix in `sidecar/src/index.ts`: capture the original `input` argument from `canUseTool` in the `PendingPermission` struct, and pass it back as `updatedInput` on the allow path.** The placeholder UX has no edit-and-approve flow, so straight passthrough is the correct semantics. Do NOT remove the `input` field from `PendingPermission` "to simplify the type" — it's load-bearing. Diagnosed empirically when an `Edit` on `README.md` threw `ZodError` on both Allow attempts (2026-04-25). Inverse asymmetry on the deny side: `sdk.d.ts:1787` types `message: string` as required (no `?`), but the SDK runtime tolerates omission and falls back to "Denied via remote control" — our code supplies a message anyway, so this isn't load-bearing in either direction. Trust neither the type's optionality nor its requiredness without runtime verification on this surface.

25. **`Query.setPermissionMode()` is a control-protocol call that requires an active iteration loop.** `sdk.d.ts:1977` types it as `setPermissionMode(mode: PermissionMode): Promise<void>` — every reasonable reader concludes it dispatches synchronously and the Promise resolves once the SDK accepts the new mode. The runtime is dependency-laden: `setPermissionMode` writes a `control_request` envelope to the SDK's transport layer; the matching `control_response` flows back on the SDK's stdout, which the `for await (const msg of q)` loop must be actively reading to dispatch. Pre-first-message that loop is blocked on `await prompt.next()` waiting for the user-message AsyncIterable to yield — so the response sits unread, the Promise queues forever, and `setPermissionMode` is silently a no-op until the user sends their first message. **`startup()` does NOT close this gap**: it spawns the CLI subprocess and awaits the initialize-handshake (so `WarmQuery.query()` returns a Query whose CLI is alive), but the iteration loop on the resulting Query still has the same blocked-on-empty-prompt-iterable problem. Even `system: init` (the canonical "session started" event) only fires after the first message arrives — direct evidence that the SDK's session lifecycle requires user input to begin. **Fix in `sidecar/src/index.ts`'s `set_permission_mode` handler: treat the sidecar's local `currentMode` variable as authoritative — update it synchronously and emit the `permission_mode_changed` echo immediately, then fire `Query.setPermissionMode()` as a best-effort fire-and-forget (`.catch(e => console.error('[sidecar] setPermissionMode:', e))`, no `.then`).** The local `currentMode` is what `canUseTool` actually reads to gate tool calls, so it IS the source of truth for our permission semantics; the SDK push only matters for the SDK's server-side mode awareness, which is a soft requirement. This matches what Claude Code TUI does conceptually — local mode state, sent to the API only when there's a turn to send. Do NOT "fix" this back to "wait for the SDK echo before mutating local state" — the user-visible symptom (Shift+Tab silently does nothing pre-first-message) returns instantly. Diagnosed empirically when the Python-side pre-warm (Phase 2 `AppController.start()` → `_session_host.start("")`) and the sidecar-side `await startup({options})` both landed and the bug persisted (2026-04-26). Sister-fix shipped at the same time: filter `{type: "system", subtype: "status"}` keepalives at `translateMessage` so they never reach `_row_from_system` (the fallback `text = subtype` path was rendering them as a continuous stream of "status / status" rows; see the 'system:status filter' paragraph in the Permission mode flow section above).
